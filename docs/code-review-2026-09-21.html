How this was done. Several findings were reproduced empirically (a throwaway script or test) rather than inferred from reading alone; those are called out inline. Findings are merged, de-duplicated, and re-ordered by severity here. IDs (H1, M3…) are labels for reference in follow-up work, not stable across reviews.

High

H1

Resuming a “Finished” book seeks to the end instead of restarting — confirmed empirically, no in-app workaround

voxcodex/screens/library.py:822, 841, 885  ·  screens/player_screen.py:150

_launch_player computes session_start_position_ms = 0 if book.is_finished else book.progress_ms (correct, for the Audible-facing session report) and then, still inside the same method, sets book.is_finished = False before constructing PlayerScreen(book, …). PlayerScreen.on_mount independently re-derives the start position from self.book.is_finished — which by then is already False — so it always takes the “resume from progress_ms” branch. For a finished book, progress_ms is at (or within ~2% of) the book's full duration. Reproduced directly: driving a finished 1,000,000 ms book through the real p keypress path recorded start_seconds == 1000.0, not 0.0.

User-visible effect: press p on a Finished book, mpv seeks to ~100%, hits EOF almost immediately, and nothing plays. On close, the end-of-book detection re-flags the book Finished and pushes ManualMarkAsFinished — so one attempt costs an Un-finish + Finish round trip to Audible and a bogus 0→end listening-session push, with no audio ever heard. Pressing u first doesn't help: it clears the flag but not progress_ms, so p still jumps to the end.

This is the same bug CodeRabbit's review of PR #2 flagged as Major (see PR2-1) — introduced by the commit that PR was reviewing (426525e), and still present after merge. Two existing tests mask it: test_resuming_a_finished_book_clears_the_flag_immediately asserts only that the flag flips, never the start position, and test_playback_close_starts_the_session_at_zero_for_a_finished_book passes while asserting a premise (“PlayerScreen.on_mount restarts a finished book from 0”) that this bug makes false. _FakeMpvPlayer.start in tests/test_library_screen.py discards start_seconds entirely, so no library-level test can catch this class of bug at all.

Fix_launch_player already owns the finished→restart decision — compute start_position_ms once and pass it explicitly into PlayerScreen (a new constructor kwarg) rather than having on_mount re-derive it from a flag the caller already mutated. Also seed _last_position_ms/_saved_position_ms from that same value (currently seeded from book.progress_ms regardless). Add a test that records start_seconds in the fake player and asserts 0.0 through the full LibraryScreen → p → PlayerScreen path.
H2

A duplicate ASIN in the library silently truncates the table, then crashes the app on the next keypress

voxcodex/screens/library.py:424–434

table.add_row(…, key=book.asin) raises Textual's DuplicateKey on a repeated key. get_library already guards the empty-ASIN case (with a comment naming this exact hazard) but nothing dedupes non-empty repeats. Reproduced with three books where two share an ASIN: the initial render raises mid-loop inside call_from_thread, leaving table.row_count == 1 while the status line still reads “3 titles” — the user's library silently appears to contain one book. The next sort/filter/open keypress then raises DuplicateKey uncaught, crashing to Textual's error screen. A repeat ASIN across pages is realistic: a purchase landing mid-pagination shifts the window, and Audible libraries can legitimately list one ASIN twice (owned + Plus catalog).

FixDedupe by ASIN in get_library (keep first occurrence, log the duplicate) the same way the empty-ASIN case is already handled. A test with two same-ASIN books should assert a sane row count and no exception.
H3

A transient mpv read failure silently rewrites the saved position to 0, and pushes that to Audible

voxcodex/screens/player_screen.py:46–52, :236–237, :273–277  ·  services/player.py:184–195

_Playback.read builds its position from MpvPlayer.get_property(…, default=0.0), which swallows MpvError and returns the default on any failed IPC round trip — a timeout, a stall during a seek, mpv exiting in the narrow window between the running-check and the read. _poll_player's except MpvError: return guard is therefore dead for the one field that matters: a failed read doesn't raise, it produces position_ms == 0. That value is written straight through to ProgressStore.set_position_ms with a fresh updated_at (so it wins by recency over the real remote value on the next load) and, on final=True, pushed to Audible's own cross-device position sync. action_close already guards this exact case for its own path (if pos_ms > 0) — the guard is simply missing on the path that actually persists on every periodic checkpoint and on close.

Net effect: a single dropped IPC read, three hours into a book, can silently erase the position everywhere — locally and on every other device. Nothing in the test suite exercises a failing read (FakePlayer.position_seconds never raises), which is why this shipped unnoticed; see also M9.

FixMake the snapshot distinguish “read failed” from “position is legitimately 0” — e.g. request the property with no default and raise MpvError on None, letting _poll_player's existing except MpvError: return skip that tick instead of committing a zero.
H4

The Amazon account password and vault password leak into Textual's worker logging

voxcodex/screens/login.py:188, :215, :253

@work(…) is used on _do_login, _do_unlock, and _do_external_login with no description=. Textual builds a worker's debug description by repr()-ing its positional arguments when none is given — reproduced empirically: Worker(…).description came back as "_do_login('me@example.com', 'SuperSecret123', 'us', 'VaultPw456')", both passwords in plaintext on a long-lived object attribute. Two concrete leak paths: Textual's devtools console (textual run --dev) logs every Worker.StateChanged event, rendering the worker's repr() — both passwords — into the devtools stream; and App._fatal_error renders any unhandled exception with show_locals=True, so a crash with a login frame or worker reference in scope on the traceback dumps the plaintext credentials to the terminal and its scrollback.

FixPass an explicit static description= on all three @work decorators (e.g. description="signing in") — Textual skips the repr() path entirely when one is given.
H5

Unvalidated DRM key/IV are newline-injectable into the mpv options file

voxcodex/services/player.py:88

_write_private_file(options_path, f"demuxer-lavf-o=audible_key={key},audible_iv={iv}\n") — key/iv come straight from decrypt_voucher_from_licenserequest, server-controlled plaintext never validated as hex. mpv's config-file parser is line-oriented and a malformed line does not abort parsing. Confirmed end to end against real mpv: a key value containing an embedded newline plus a script=/path/evil.lua line causes mpv to load and execute that Lua script — code execution as the user running VoxCodex. This requires a hostile or compromised license response (Audible's backend, or a MITM of it), which is a strong precondition, but the file's own docstring already defends a strictly weaker threat model (a local user reading /proc/<pid>/cmdline), so the gap is inconsistent with the posture the rest of the module invests in.

FixReject anything that isn't a plain hex string before writing it into the options file, for both key and iv — raise MpvError on a failed match rather than passing the value through.
H6

The stream URL is passed to mpv as a bare positional argument with no -- terminator

voxcodex/services/player.py:90–101

cmd = ["mpv", …, f"--include={options_path}", source] — for a streamed title, source is license.content_url, server-controlled. mpv parses any positional argument starting with - as an option rather than a filename; confirmed with real mpv that a leading-dash argument such as --script=/path/evil.lua is executed as such. A content_url value beginning with - is therefore code execution, under the same server-compromise precondition as H5. The downloaded-file case is unaffected only because DOWNLOADS_DIR paths are always absolute and don't start with -.

FixInsert a literal "--" immediately before source in the argument list, so mpv treats everything after it as positional regardless of leading characters.

Medium

M1

get_license is missing the status == "Exists" guard its sibling parser requires

voxcodex/services/api.py:260–264  vs.  services/progress.py:199–205

progress._existing_last_position_heard parses Audible's last_position_heard shape and explicitly rejects any record whose status isn't "Exists" (a never-played title returns a DoesNotExist record). get_license parses the same field shape with no such guard, so a licenserequest response carrying a DoesNotExist record with a fresh timestamp could feed _resolve_progress_ms a bogus “most recent” position of 0, silently resetting a real resume point. Whether the license response actually includes status wasn't confirmed against a live capture; the guard is cheap regardless of trigger likelihood.

FixApply the same status == "Exists" check in get_license, ideally by sharing one parser between the two call sites.
M2

Remote-position lookups send every ASIN in the library as one unchunked query string

voxcodex/services/progress.py:111  ·  screens/library.py:276

fetch_remote_annotations(self.api, [b.asin for b in books]) joins the entire library into one asins=… parameter with no chunking. At ~11 bytes per ASIN that's several KB of query string for a several-hundred-title library, plausibly past a gateway's request-line limit. The failure path swallows everything (except Exception, logged at DEBUG), so on a large library the whole remote-position feature and most_recent_external_play silently stop working, with zero indication to the user — degrading exactly at the library size where it matters most. Independently identified by two of the four reviewers from different call sites.

FixChunk the ASIN list (e.g. 100 per request) inside fetch_remote_annotations and merge the results; log at WARNING when a chunk fails outright.
M3

A non-JSON 200 response crashes the player/chapter workers instead of showing an error

voxcodex/services/api.py:237, :449

audible.client.convert_response_content falls back to returning raw text when a 200 body isn't valid JSON (a captive portal, a proxy error page, an Amazon maintenance page). Neither get_license nor get_chapters guards against that: indexing a str as if it were the expected dict raises TypeError/AttributeError, neither of which is in _PLAYER_OPEN_ERRORS or _CHAPTER_FETCH_ERRORS — so it escapes the worker's error handling and the user gets no message at all, rather than “Could not start playback…”. progress.fetch_remote_annotations already guards exactly this hazard (isinstance(resp, dict)); the other two call sites don't.

FixAdd an isinstance(…, dict) guard (raising a typed error) at both call sites, or widen the call-site exception tuples to include TypeError/AttributeError.
M4

most_recent_external_play's premise is now false, and the feature it feeds is dead, write-only state

voxcodex/services/progress.py:163–183  ·  services/settings.py:89–101

Its docstring says it finds “the book you most recently played somewhere other than this app”, on the premise that VoxCodex's own plays don't reach the lastpositions endpoint. That was true before the mid-book sync push shipped; it no longer is — push_position now writes there, and the project's own capture notes confirm the write is visible via GET annotations/lastpositions within about a second. So today, right after any VoxCodex session, this function returns the book just played in VoxCodex, contradicting its own name. Actual severity is blunted because nothing reads last_played_externally/last_played_in_app anywhere in the app — they're written on every library load and every playback start and never consulted, so this is presently dead weight (an extra settings read-modify-write per library load) rather than a user-visible bug.

FixEither delete the last_played_* pair and this function outright, or make the “external” determination exclude records within a small tolerance of this app's own ProgressStore timestamp for that ASIN, and correct both docstrings either way.
M5

ProgressStore has no type guard on cache entries, unlike its siblings — a malformed entry takes down the whole library load

voxcodex/services/progress.py:71–72, :82–94

get_position_ms does int(self._data.get(asin, {}).get("position_ms", 0)) with no shape check beyond “top level is a dict”. A valid-JSON, wrong-shape entry — {"B001": 5000}, or {"B001": {"position_ms": "abc"}} — raises AttributeError/ValueError. This is called once per book on every library load, so one bad entry breaks the entire load, with no self-healing since the file is never rewritten from a clean state. The adjacent get_updated_at in the same class, and settings._last_played, both already guard the equivalent conversion with isinstance + try/except — this is the one place in the module that doesn't.

FixApply the same isinstance + try/except (TypeError, ValueError) pattern here, and have set_position_ms replace a non-dict entry rather than attempt to mutate it.
M6

MpvPlayer.start() can leak a temp dir holding the DRM key, and a non-MpvError startup failure wedges the player screen forever

voxcodex/services/player.py:81–107  ·  screens/player_screen.py:169–175

start() creates a 0700 temp dir and writes the 0600 key/IV options file, then calls subprocess.Popen outside the surrounding cleanup try. Reproduced: pointing Popen at a nonexistent binary raises FileNotFoundError and leaves the temp dir (with the plaintext key inside it) on disk under /tmp until the next reboot — nothing ever reclaims it, since a fresh MpvPlayer is constructed per playback. Separately, PlayerScreen._start_player only catches (MpvNotFoundError, MpvError); a real-world trigger for the same failure (mpv removed/renamed between the constructor's shutil.which check and this call, or a resource limit) escapes as an unhandled OSError, is swallowed by the worker's exit_on_error=False, and leaves the screen reading “Starting player…” indefinitely with no error and no retry.

FixMove the Popen call inside the existing cleanup try (or wrap the whole setup block and call self.stop() on any exception), and widen _start_player's except clause to OSError.
M7

Two downloads racing on the same book collide on one temp filename, losing the download and orphaning its voucher

voxcodex/services/download.py:57–59, :75, :105–114  ·  screens/library.py:600–643

The temp path is deterministic ({asin}.part) with no in-flight guard on either the app-instance level (sweep_stale_downloads on startup globs *.part and removes anything matching) or the single-instance level (pressing d twice on the same book starts a second worker in the same exclusive group; Textual's Worker.cancel() only flags the thread, which keeps running). In either case, one download's tmp_path.unlink() (its own cleanup, or the stale-sweep) can remove the file out from under the other, which is still writing to the now-unlinked inode; that download completes, writes its voucher successfully, then tmp_path.replace(audio_path) — sitting outside the surrounding except — raises FileNotFoundError. The download is lost with a cryptic error, and the voucher (the AES key) it already wrote is left permanently on disk with nothing ever sweeping it, invisible to is_downloaded() since that checks both files.

FixUse a unique temp name per attempt (tempfile.mkstemp(dir=DOWNLOADS_DIR, suffix=".part") — the *.part sweep glob still matches), move the replace() inside the cleanup try so a failure there also removes the voucher, and add an in-flight-ASIN guard in action_download_selected to reject a same-book double-press with a status message instead of racing.
M8

Transport keys, close, and unmount all do blocking mpv IPC on the Textual event loop

voxcodex/screens/player_screen.py:204–214, :284, :413–430

_poll's own docstring says reads “must not run here — a wedged mpv would freeze the whole TUI”, but every _control call (every transport action — play/pause/seek/speed) does exactly that: action_toggle_pause alone is two synchronous IPC round trips, each up to the full command timeout, contending with the poll worker for the same I/O lock. action_close is worse — a position read plus stop()'s socket write, process wait, and directory removal — so pressing q against a wedged mpv can freeze the entire TUI for several seconds. on_unmount does the same on app quit.

FixRoute _control/stop() through a thread worker the same way the poll path already is, so the event loop never blocks on the IPC socket.
M9

A dead code path in _tick is what most of the player-screen test suite actually exercises — masking H3 from the tests

voxcodex/screens/player_screen.py:253–267  ·  tests/test_player_screen.py

Production code never calls _tick() without a snapshot — the only real caller is the poll worker, which always passes one. The snap is None branch (its own synchronous read, no worker involved) exists, per its own docstring, for “the first render, and tests”, but there is no first render that takes this path. The practical consequence: nearly every behavioral test in the file (test_tick_*, the chapter tests, the checkpoint tests, the sleep-timer tests) calls screen._tick() directly and therefore never exercises the real worker → call_from_thread → _tick(snap) pipeline that production traffic actually takes — which is exactly why H3's failure-swallowing shape was invisible to the suite.

FixDelete the snap is None branch, make snap a required parameter, and re-point the affected tests at the real _poll() path (or construct a _Playback snapshot explicitly and call _tick(snap)).
M10

The log file loses its 0600 permissions on the first rotation

voxcodex/app.py:82–94

The log file is deliberately pre-created and chmod'd 0600, with a comment explaining it can contain the account email and (in debug mode) raw API response bodies. But RotatingFileHandler.doRollover renames the current file away and reopens the base name through FileHandler._open, which calls plain open() — umask defaults apply. Reproduced: after a rotation, both the live log and its .1 backup come back at 0644. DATA_DIR being 0700 limits the blast radius on a typical single-user box, but the hardening is silently and completely undone the first time the file crosses 1 MB — trivially reached under VOXCODEX_DEBUG.

FixSubclass the handler to re-chmod the file to 0600 inside _open() after calling super()._open().
M11

chapter_cache.load() raises on a non-dict cache file, despite documenting that it never raises

voxcodex/services/chapter_cache.py:35–49

The except tuple omits AttributeError; a cache file whose top-level JSON is valid but not an object ([], "hello", null) makes data.items() raise exactly that. Reproduced against all three shapes. This runs unguarded in LibraryScreen.__init__, which itself is constructed right after a successful login — so a cache file damaged by truncation, a sync-tool mishap, or a future schema change takes the app down immediately post-login with no recovery path short of manually deleting the file. The sibling library_cache.load() doesn't have this hole; the two disagree.

FixAdd if not isinstance(data, dict): return {} after parsing (and/or add AttributeError to the except tuple) — and add tests/test_chapter_cache.py, which doesn't currently exist despite the repo's one-file-per-module test convention (see also the coverage-gaps note below).
M12

playback_speed/playback_volume crash on a corrupted-but-parseable settings value

voxcodex/services/settings.py:76, :83

Both properties do an unguarded float(…). Reproduced against {"playback_speed": "1.5x", "playback_volume": null}: both raise (ValueError and TypeError respectively). PlayerScreen.__init__ reads both on the main thread when opening a book, so a corrupted value here takes the whole app to the fatal-error screen. M13

The table's active filter and the downloaded-size label go stale after download, delete, unmark, or a playback session

voxcodex/screens/library.py:664, :677, :706, :731, :862

These five handlers mutate is_downloaded/is_finished/progress_ms and then call _refresh_table(), which re-renders the existing self._filtered list without recomputing it and never updates the sort/filter label. Reproduced: with the filter set to “Downloaded”, downloading a book leaves the row count at 0 (the row never appears); deleting the only download leaves the size label reading the pre-deletion total. M14

A corrupt or unreadable download voucher hangs the play flow forever, with no error shown

voxcodex/screens/library.py:47–49, :749  ·  services/download.py:144–148

load_voucher can raise json.JSONDecodeError (a ValueError) or OSError, and neither is in _PLAYER_OPEN_ERRORS. Reproduced: with a malformed voucher, pressing p leaves the status line reading “Opening license for …” permanently — the worker's exception is swallowed by exit_on_error=False, so the user gets no feedback and every retry hangs the same way. M15

“Unmark finished” (u) can leave a book unreachable by any filter

voxcodex/screens/library.py:551–560, :721–733

action_unmark_finished clears is_finished but leaves progress_ms at ~100%. The “Finished” filter matches on is_finished OR progress_pct >= 98; “In progress” requires not is_finished AND 0 < pct < 98. A book at 100% with the flag just cleared therefore still matches only “Finished” — not “In progress”, not “Not started” — and pressing u again is a no-op, so the state is permanently unreachable by any further keypress. This directly defeats the feature's own stated purpose (undoing a mis-fired 98% end-of-book heuristic). action_delete_finished_downloads, separately, checks bare is_finished — so the bulk-delete action and the Finished filter already disagree about what “finished” means.

FixPick one definition of “finished” and use it consistently — e.g. have the filter consult is_finished alone (the pct fallback becomes redundant once library-load already sets the flag from percent_complete >= 98), or have u also reset the tracked position.
M16

The Chapter column doesn't advance after a listening session

voxcodex/screens/library.py:845–862

_on_progress updates book.progress_ms and rebuilds the table on close, but never recomputes book.chapter_current. Reproduced: a 3-chapter book listened to most of the way through returns to the library still showing “0/3” (chapter 0 is a real, non-placeholder value in this model, so it doesn't fall back to “unknown”).   • L8 · player_screen.py:407–411 — _flush_progress marks progress as saved even when the save callback raised, suppressing the next periodic retry at the same position. Move the “saved” bookkeeping into the success path only.
  • L9 · player_screen.py:274, :282 — The sleep timer and checkpoint counter assume exactly one tick per second, but a poll that takes longer than a second (four IPC round trips under load) is skipped entirely rather than counted — both drift long. Use monotonic-clock deltas instead of a fixed per-tick decrement.
  • L10 · player_screen.py:301–313 — The chapter row goes stale when the current-chapter lookup returns None (seeking before the first chapter's start) — the previous chapter's text is left on screen with no fallback branch.
  • L11 · download.py:87, :101 — content-length is compared against decoded byte count; httpx negotiates gzip by default and iter_bytes() yields decoded bytes, so a CDN that ever compresses would make every download fail as “truncated”. Compare against resp.num_bytes_downloaded, or request Accept-Encoding: identity.
  • L12 · auth.py:178–193 — An auth file left at 0644 by a pre-hardening install is never tightened on load, only re-chmod'd on the next fresh login. Mitigated by CONFIG_DIR being 0700, so this is defense-in-depth only; chmod the existing file on load() too.
  • L13 · auth.py:62–64 — CAPTCHA/OTP verification-page text is logged at INFO unconditionally, and Amazon's page text typically includes a masked destination (partial email/phone) — mild PII in a persistent log file. Demote to DEBUG alongside the other login diagnostics.
  • L14 · auth.py:109, :128–135 — The login-diagnostics monkeypatch resolves five private audible.login names outside its own try, while already holding a module lock — a future rename in that dependency would raise AttributeError and leave the lock permanently held, breaking diagnostics (and, transitively, login) for the rest of the process. test_audible_surface.py guards the names in CI, which is why this hasn't bitten in practice; move the lookup inside the try so it degrades instead of failing closed.
  • L15 · api.py:235, :295, :448 — ASINs are interpolated into request paths with no percent-encoding. The underlying client builds the URL via a raw-path copy, so a value containing ? or # would inject a query/fragment. Values originate from Amazon over TLS, so this is theoretical, but get_library already validates ASIN presence — validating its shape there too is nearly free.
  • L16 · api.py:462–492 — _book_from_item's type coercion is inconsistent: title defaults via .get(…, "Untitled") (which doesn't catch an explicit null, unlike the or "" pattern used two lines away for subtitle), and runtime_min/percent_complete are used arithmetically with no numeric coercion, unlike the equivalent chapter-parsing code a few lines down.
  • L17 · modals.py:50, :99 · library.py:681 — Modal message text is rendered as Rich markup, and at least one call site interpolates a publisher-supplied book title into it. Confirmed: a title containing [/]-shaped text raises a MarkupError inside the confirm dialog; common Audible suffixes like [Unabridged] happen to survive only because of Rich's tag-character rules, not by design. Render the message Static with markup=False, or escape the interpolated value.
  • L18 · modals.py:12, :77 — Neither modal is dismissible by keyboard. A lower screen's bindings don't reach an active modal, so the only way out of a CAPTCHA/OTP prompt or a delete-confirmation is to tab to a button. Add an escape binding to both.
  • L19 · chapter_cache.py:25–28 · library.py:370, :390, :795 — chapter_cache.save() iterates a dict a different worker thread can concurrently mutate, which can raise RuntimeError: dictionary changed size during iteration — not caught by save()'s except OSError, so that session's chapter cache is silently not written. Snapshot with dict(chapters_by_asin) before iterating.
  • L20 · library.py:600–665 — Switching the active download mid-flight can hide the new download's progress bar and post a stale “Downloaded: …” status for the cancelled one while the new one runs invisibly. Guard the completion callbacks to no-op unless they match the currently-active download.
  • L21 · library.py:319–320, :663 — A library refresh completing mid-download orphans the in-flight Book object — the download's completion handler mutates a Book no longer present in self._books, so the finished download doesn't show as downloaded until the next manual refresh. Re-resolve by ASIN against the current book list in completion handlers instead of holding the object.
  • L22 · library.py:274 — A successful-but-empty library fetch overwrites a good offline cache with nothing. If get_library's first page legitimately returns no items (a transient backend quirk, not “this library is empty”), library_cache.save([]) destroys the last known-good cache; guard with if books: library_cache.save(books).
  • L23 · library.py:583, :546 — Two DOM queries reached from a background worker aren't guarded against NoMatches the way the rest of the file's worker callbacks deliberately are (with an explaining comment). Harmless today under exit_on_error=False, but inconsistent with the pattern established everywhere else in the file.
  • L24 · models.py:46–72 — Minor display inconsistencies in Book: an unknown runtime renders as “0m” while an unknown remaining-time renders as an empty string; and time_left_display can report “done” for a book with well under a minute remaining that has never actually been started, from rounding.
  • L25 · settings.py:70–72 — Dead code: Settings.reload() has zero callers anywhere in the app, despite being the natural fix for the cross-instance staleness that exists wherever more than one Settings is constructed.
  • L26 · progress.py:120, :208 · api.py:31–35, :248 · models.py:21–22 — A cluster of dead code: positions_from_annotations and fetch_remote_positions have no production caller (only tests); the quality parameter threaded through download_book/get_license is never overridden by any call site; License.codec is written to the voucher and never read back; Book.cover_url is parsed and stored but never rendered; Book.local_audio_path/local_voucher_path are never set or read; three of the four LIBRARY_RESPONSE_GROUPS fields (customer_rights, product_desc, product_extended_attrs) are requested but never consumed, adding meaningful per-item payload across a full library fetch for nothing.
  • L27 · app.py:68–69 — Login's success handler uses pop_screen() + push_screen() where the file's own login.py deliberately uses switch_screen instead (with a comment and a regression test explaining why). Worth making consistent, and it removes a dependency on the modal pop having already landed for the external-login flow.

Test coverage gaps worth closing before 1.0

The suite is genuinely strong where it exists — 367 tests, real Pilot keypresses rather than direct action_* calls, careful Fake* doubles, and good coverage of search/sort/filter and sync-failure statuses. The gaps below are specific and line up directly with findings above, not general “write more tests” advice:

  • No test asserts the mpv start position through the real library→player path (_FakeMpvPlayer.start in tests/test_library_screen.py discards start_seconds) — this is precisely what let H1 ship, and one existing test (test_playback_close_starts_the_session_at_zero_for_a_finished_book) currently asserts a premise the bug makes false.
  • No test drives a failing mpv property read (FakePlayer.position_seconds never raises) — the exact gap that hid H3, compounded by M9's dead test path.
  • voxcodex/services/chapter_cache.py has no dedicated test file at all, breaking the repo's stated one-module-one-test-file convention and directly responsible for M11 going unnoticed — its sibling library_cache.py has the equivalent “unrecognized shape” test that would have caught it.
  • services/auth.py's login/login_external are untested — swapping the OTP and CAPTCHA callbacks in LoginCallbacks would pass the whole suite unnoticed.
  • No test for a duplicate-ASIN library (H2), a corrupt voucher (M14), a double-press download (M7), or chapter-count staleness after playback (M16).
  • No test for a corrupted-but-valid settings value (M12) — test_settings.py covers a corrupt JSON file but not a corrupt typed value.
  • No test asserts log file or cache file permissions after rotation/write — the repo tests 0600 on the auth file, vouchers, and the mpv options file, but not the log file (M10) or chapter_cache.json/library_cache.json.
  • Nothing asserts the request identity headers documented as load-bearing in api.py's own comments (the device user-agent, the licenserequest headers) actually get attached to outgoing requests.
  • FakePutClient discards response_callback, so the “propagates HTTP errors” tests around the PUT endpoints verify the fake, not that raise_for_status is actually wired up in production.

What's already solid

Deliberately not flagged — every reviewer called this out independently, and it's worth preserving as the codebase keeps growing:

  • No unsafe deserialization anywhere in the codebase — every on-disk cache goes through plain json.loads into an explicit dataclass constructor, never pickle/eval/__reduce__.
  • Credential and DRM-key file handling is careful and consistent: the auth file is pre-created at 0600, data directories are chmod'd 0700 on every startup, atomic_write_text genuinely lands files at 0600 via mkstemp + os.replace, and _log_cvf_page deliberately logs value lengths, not values.
  • The voucher-before-rename ordering in the download pipeline, and the .part sweep on startup, are correct and well-reasoned — the gaps found here (M7) are in the concurrency around that design, not the design itself.
  • DEBUG-level audible logging is opt-in behind an explicit environment variable with a warning, not on by default — the exposure C1 flagged last review is fixed and stayed fixed.
  • Every prior review's Critical, High, Medium, and Low items, and the entire mid-book sync investigation, are genuinely closed — verified by re-reading, not just by trusting TODO.md's own claim.
  • The module docstrings in progress.py and chapter_cache.py that document past bugs and design tradeoffs are exemplary — several findings above exist specifically because a docstring's claim (“never raises”, “this app's own plays don't reach this endpoint”) has drifted from the code beneath it, not because the original reasoning was wrong.

Suggested order of work

  1. H1 first. It's the one external reviewers already flagged once, it's a released regression (not a pre-existing gap), and it's the smallest diff of the six High findings.
  2. H3 + M9 together. Fix the silent zero-position write, then delete the dead _tick(snap=None) test path so the fix (and future regressions in this exact spot) is actually covered.
  3. H5 + H6 — the mpv argument-injection pair. Both are one-line fixes (a regex guard, a "--" terminator) closing a code-execution primitive each; do them together since they're the same investigation.
  4. H2 + H4. Dedupe-by-ASIN in get_library, and a description= on the three login workers — both small, both isolated.
  5. M13 + M15 + M16 together. All three are “local state didn't refresh after an action” bugs in library.py; worth one focused pass since the fix for M13 (call _apply_filters_and_sort) likely covers M16's symptom too once chapter state is included in what gets recomputed.
  6. Everything else, roughly by severity — none of the remaining Mediums or Lows are urgent individually, but the tests/test_chapter_cache.py gap and the log-rotation permission regression (M10) are cheap enough to fold into whichever PR touches those files next.
